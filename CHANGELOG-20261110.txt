Search audit (every search path checked - POS box, browse box, autocomplete API, Inventory,
barcode/SKU scan, Sets, Sales)

Found and fixed
- Multi-word queries were matched as one contiguous substring everywhere: 'rtx 5060' or
  'gaming sandal' found nothing unless the name contained that exact spacing/order. Now every
  typed word must match somewhere (AND across words, OR across name/SKU/barcode/brand).
- Case: SQLite LIKE/LOWER only fold ASCII, so uppercase Cyrillic (ШИРЭЭ, ХАР) returned 0 hits
  against names stored as "Ширээ". A norm() UDF (Python casefold) is registered on each
  connection and all searches compare norm(column) - Cyrillic now matches in either case.
- User-typed % and _ were live SQL wildcards: q='_' matched 52 products, q='%' matched all.
  They are escaped and used with ESCAPE '\', so they search literally.
- Browse grid priced everything 0₮: /pos/search returns price/price_num but the JS read
  p.amount. API now returns amount as well.
- Sets were searched two different ways - server used whole-query substring, the browse box JS
  used all-words - so results changed depending on whether the grid was re-rendered. set_catalog
  now uses the same all-words rule and also searches set description/components.
- /pos/scan compared barcode/SKU with LOWER() (ASCII only) -> norm() equality.
- Sales search only covered ref/phone/note and was single-substring; it now also matches the
  item names stored on the sale (sale_items.name) and applies the word/case/escape rules.
- Race conditions: POS live box, POS browse box and Sales live search had no ordering guard, so
  a slow response for an older term could paint over a newer one (the "works then doesn't"
  symptom) and a failed fetch was an unhandled rejection. All three now use a sequence token,
  re-check the current input, and show an error on failure.
